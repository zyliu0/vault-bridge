# v16.4.0 field-agent handoff: how to make sure every project ends up in the right shape

This release closes the eight bugs from the 2026-05-04 pipeline format
audit. After updating, several file-type events that used to silently
skip will now produce real notes — but the **existing vault is full of
notes written under the old behaviour**. The handoff plan below shapes
the post-update workflow per project so the vault converges on the new
coverage.

## What changes for users after v16.4.0

| Change | Effect on existing notes | Effect on future scans |
|---|---|---|
| HEIC end-to-end | None | Photos with `.HEIC`/`.HEIF` source paths now produce embedded-image notes |
| XLSX text + images | None | Spreadsheets get a real text body + embedded images |
| `.xls` LibreOffice fallback | None | `.xls` files that xlrd couldn't open now produce text |
| `.rtf` registered | None | `.rtf` events that previously skipped as "unknown file type" now produce text |
| SKP metadata stub | None | SketchUp files get a metadata note instead of "unknown file type" |
| 3DM warning | None | `.3dm` notes now carry a `cssclasses: warnings` line in `warnings[]` flagging the metadata-only limit |
| Size-gate reclassification | None | Notes that were previously skipped as `no_content` due to small textures now report `below_size_gate` |
| Setup pipeline probe | None | Future setups surface broken handlers loudly |

The headline: **all changes are forward-looking**. No existing notes
get rewritten, no frontmatter changes, no breaking schema migration.

## Field-agent workflow — the right shape per project

The field agent (you, running `/vault-bridge:retro-scan` per project)
needs a deliberate plan because v16.4.0 unlocks file types that were
previously dropping silently. Here's the per-project decision tree.

### Step 0 — update the plugin

```bash
/vault-bridge:self-update
```

After update, run the new pipeline probe **before** any scans:

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/handler_probe.py --workdir "$(pwd)"
```

You should see `[OK]` for txt, md, png, jpg, jpeg, gif, webp, bmp,
tiff, tif. `[OK]` for rtf only when `striprtf` is installed OR
`soffice` is on PATH; otherwise `[FAIL] missing tool: striprtf …`.

If any handler reports `[FAIL]` with a missing tool, fix that
**first** — running scans against a broken handler still produces
empty notes. Setup will offer to install the tool via brew/apt.

### Step 1 — list projects

For each project the agent has previously scanned, decide which of
three buckets it belongs in:

#### Bucket A — projects rich in the previously-broken file types

Architecture / design projects with HEIC site photos, XLSX size
schedules, SketchUp models, RTF memos, or `.xls` budgets fall here.
Examples from prior field reports: ILE, SZB, JDZ, LAGI, SSS, SIM
(SketchUp-heavy).

**Action:** `vault-bridge:reconcile <project> --re-read`

The reconcile pass with `--re-read` will:
1. Audit existing notes against the schema.
2. For notes whose `source_path` resolves and which previously
   skipped (`no_content`, `below_size_gate`, or had garbled extract
   text from v16.3.0), re-run `scan_pipeline.process_file`.
3. Rewrite the body with the now-working extractor's output.
4. Preserve curated filenames via `vault_paths.lookup_existing` +
   `vault_writer.rewrite_in_place` (v16.3.0 SSS-F).

This will produce **new content** for the previously-skipped events
without orphaning the curated notes.

For the unscanned events (the ones that never made it into the
vault because they skipped), follow up with:

`vault-bridge:retro-scan <project>` with no special flags — the
scan pipeline now picks them up automatically.

#### Bucket B — projects already complete, no relevant file types

Projects whose archive is mostly PDF / DOCX / PPTX / images that
v16.3.0 already handled correctly. Examples: pure-text writing
projects, photography projects with only JPG/PNG.

**Action:** no immediate action. The next regular `heartbeat-scan`
will pick up any new file types as they arrive.

#### Bucket C — projects that haven't been scanned at all

**Action:** standard `vault-bridge:retro-scan <project>` after
updating. v16.4.0 covers everything v16.3.0 did, plus the gaps
above.

### Step 2 — known limits to communicate

Two file types have **design limits**, not bugs, that the field
agent should mention to the user before running:

- **`.3dm` (Rhino):** metadata-only. The note will list the layer
  roster, object counts, and ApplicationName but cannot include a
  visual rendering. v16.4.0 adds an explicit warning to the note's
  `warnings[]` so the user knows. To get visual screenshots, Rhino
  CLI (commercial) is needed — out of scope for vault-bridge.
- **`.skp` (SketchUp):** metadata-only unless the user installs
  `skp2obj` or `skp2unity` on PATH. v16.4.0's stub handler emits a
  metadata note explaining the situation.

For projects heavy in either type (SSS, ILE, CCJ, ZG for `.3dm`;
SIM for `.skp`), let the user know the notes will be metadata-only
upfront so they don't expect visual content.

### Step 3 — recommended ordering

1. **Update + run pipeline probe** — confirm baseline health.
2. **Heaviest impacts first.** Projects in Bucket A get reconcile
   `--re-read` runs. Order the bucket by archive recency so the
   most-active project gets attention first.
3. **Net-new scans for projects without prior runs.** Standard
   retro-scan flow; v16.4.0 produces strictly more coverage than
   v16.3.0.
4. **Follow up by-exception only.** Bucket B projects need no
   action; the next heartbeat picks them up automatically.

### Step 4 — what NOT to do

- **Do NOT mass-delete + re-scan.** Reconcile preserves curated
  filenames (SSS-F); a delete + re-scan would orphan the
  translated names architects spent time picking.
- **Do NOT skip the pipeline probe.** Running scans without a
  green probe just produces empty notes silently.
- **Do NOT install ODA File Converter on the user's behalf.** It
  has a click-through EULA. The setup wizard handles this with
  user consent; the field agent doesn't autopilot it.

## Memory-report fields to track

For each project re-scanned post-v16.4.0, the memory report should
include:

```yaml
v16.4.0_reread:
  events_re_read: <int>          # source_path resolved and re-extracted
  events_newly_indexed: <int>    # source_path not previously in scan index
  events_reclassified_below_size_gate: <int>  # AUDIT-1c
  events_with_3dm_warning: <int>              # AUDIT-6
  events_with_skp_metadata: <int>             # AUDIT-5
  external_tool_missing: [<tool>, ...]        # surfaced via probe
```

Per-project: this lets the next field report compare v16.3.0
coverage to v16.4.0 coverage cleanly.

## Quick-reference command summary

```bash
# Update the plugin
/vault-bridge:self-update

# Verify pipeline health
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/handler_probe.py --workdir "$(pwd)"

# Bucket A — reshape an existing project
vault-bridge:reconcile "<project-folder>" --re-read

# Bucket A follow-up — pick up previously-skipped events
vault-bridge:retro-scan "<project-folder>"

# Bucket C — net-new project
vault-bridge:retro-scan "<project-folder>"
```

The whole point of v16.4.0 is that the **scan command flow is
unchanged**. The changes happen inside `scan_pipeline.process_file`
and the handler templates; the user-facing commands are the same.
The field agent's job is to know which projects have files that
were previously dropping silently and run reconcile against them.
